# Codebase ⇄ Documentation Audit

## Context

You asked: *"is everything up to date as per the `update/` folder and `update/changes/` folder?"*

The audit compares **what's in the docs** against **what's actually in the repo**. Two documentation sets coexist:

- **`update/`** — describes **ClarityAI v0.1** (web-first Socratic tutor, Gemini 2.0, FastAPI middleware). Claims **Phases 1–7 complete**.
- **`update/changes/`** — describes **LUMOS v4** (a *pivot* to a hardware-first stack with Groq + Cartesia + Redis + pgvector + a brand-new `lumos-backend/` layout). Marked **pre-build** across all 7 phases.

Headline: the **ClarityAI v0.1 codebase is real and matches its docs**. The **LUMOS v4 pivot is documented but virtually unbuilt** — zero Groq, Cartesia, Redis, or the planned `lumos-backend/` module structure exists.

## 5. Bottom line

- **Up to date with `update/` (v0.1)?** Largely yes. One stale doc (`IMPLEMENTATION_PLAN.md`) and one off-topic doc (`PROJECT_CONTEXT.md`). Runtime hygiene items in `KNOWN_ISSUES.md` still apply.
- **Up to date with `update/changes/` (v4 pivot)?** **No** — the pivot is documented but not started. Database foundation is partially aligned (devices, pairing, exam_track column, pgvector); everything else (Groq, Cartesia, Redis, MSM cache, orchestrator, classifier, formatters, R2, two-track routing, latency instrumentation) is unbuilt.

**v4 is confirmed as the actual product direction.** The repo therefore sits at "end of v0.1, before v4 build starts." Concretely, the remaining gap to ship v4 is:

1. **Backend rewrite** — flat `backend/` → modular `lumos-backend/` (gateway, orchestrator, providers, classifiers, formatting, storage, workers, schemas, prompts).
2. **LLM stack swap** — Gemini 2.0 Flash → Gemini 2.5 Flash (Turn 1) + Groq Llama 3.3 70B (Turn 2+) + Gemini 2.5 Pro (escalation) + Cartesia Sonic TTS.
3. **State layer** — add Redis (MSM cache, attempt counters, 3-layer Gemini context cache, session profiles).
4. **DB extensions** — `turns`, `question_attempts`, `memories` (pgvector) tables on top of migration 002.
5. **Pipeline pieces** — query classifier (6-type taxonomy), nudge logic (attempt-count → HINT/FULL/DIRECT), validator (confidence gate + voice/TFT/LaTeX checks), two-track formatter, Google Search grounding for conceptual.
6. **Blob storage** — Supabase Storage → Cloudflare R2 (per LUMOS spec).
7. **Hardware target shift** — ESP32-CAM firmware → ESP32-S3 + INMP441 + OV5640 + MAX98357A + ILI9341 + WS2812B (matches HARDWARE_CONTEXT.md frame protocol exactly).
8. **WebSocket consolidation** — drop `/ws/client/{id}` and `/ws/hardware/{id}`; keep only `/lamp/ws` with the LUMOS binary-frame protocol and device_jwt auth.
9. **Latency instrumentation** — TTFT, total_ms, cost_usd per turn; targets <1.5s (Turn 1) and <500ms (Turn 2+).

This audit is the deliverable — no doc or code edits made. Use it as the input when you're ready to scope the v4 build.

## Addendum — Phases 2–6 build completed (2026-05-26, same day)

After Phase 1 the user opted to push straight through Phases 2–6 with the
caveat that real API keys would land later. Every layer was built with a
working in-process / file-backed fallback so the gateway boots without any
external infra.

- ✅ **Phase 2 — Short-term memory.** [`app/storage/redis_client.py`](../lumos-backend/app/storage/redis_client.py) ships `MemoryRedis` (in-process LPUSH/LTRIM/EXPIRE) as fallback when `REDIS_URL` is unset or `redis-py` is missing. [`app/services/memory.py`](../lumos-backend/app/services/memory.py) caps history at 3 turns / 24 h TTL and renders chronologically into the prompt. Resilient to Redis outages — the live response path never breaks. 7 new tests, all green.
- ✅ **Phase 3 — Validator + Pro escalation.** [`app/services/validator.py`](../lumos-backend/app/services/validator.py) strips markdown / `$math$` from speech, caps voice + TFT length, rejects forbidden mathtext commands (`\boxed`, `\tfrac`, `aligned/cases/array` envs), and pre-renders LaTeX to catch parse failures. `LlmReply.is_confident: float` drives escalation: `< 0.60` → `gemini-2.5-pro` re-roll, configurable via `CONFIDENCE_ESCALATE_BELOW`. 10 new tests covering each gate.
- ✅ **Phase 4 — Classifier + grounding + vector memory.** [`app/services/classifier.py`](../lumos-backend/app/services/classifier.py) is a keyword heuristic (LLM-based classifier deferred) emitting `(exam_track, needs_grounding)`. The Gemini provider gained `enable_grounding: bool` → wires Google Search tool when the classifier opts in. [`app/storage/vector_memory.py`](../lumos-backend/app/storage/vector_memory.py) implements per-user long-term memory with a JSONL file store + cosine ANN; embedder is `text-embedding-004` when keyed, `HashEmbedder` (deterministic) otherwise. Top-K recall (k=3) prepends to the prompt alongside short-term history. 11 new tests.
- ✅ **Phase 5 — Persistence.** [`app/storage/blobs.py`](../lumos-backend/app/storage/blobs.py) ships `LocalBlobs` (filesystem) and `S3Blobs` (`aioboto3`) behind one async `put(key, body, content_type)` interface. [`app/storage/turns_repo.py`](../lumos-backend/app/storage/turns_repo.py) writes a JSONL ledger per device — row shape mirrors the Postgres schema from `BACKEND_DESIGN §4.7`. [`app/services/persistence.py`](../lumos-backend/app/services/persistence.py) `commit_turn()` runs as a background `asyncio.create_task` so blob uploads + ledger writes never touch the hot path. 5 new tests.
- ✅ **Phase 6 — Sentence-level streaming TTS.** [`app/services/streaming_parser.py`](../lumos-backend/app/services/streaming_parser.py) is a focused state machine that watches the LLM byte stream for the `"speech":"..."` field, handles JSON escapes and split-across-chunk-boundary `"speech"` keys, and emits each complete sentence as it lands. Opt-in via `STREAMING_TTS=1`: when set, the orchestrator spawns a `_speak_streaming` task that drains a sentence queue while the LLM is still generating, so TTS starts on the first sentence (~700 ms after AUDIO_END) instead of waiting for full JSON (~2 s). 7 new tests covering chunk-boundary detection, JSON escape handling, run-on flush.

requires only the env var(s) below; no code change needed:
